Setup & readback

Run the private service

The browser never calls source APIs or connects to Neon. This file also contains the Node service. Save it as rooms.html and run these commands in its directory with Node.js 20+:

npm install --no-save pg

rooms() {
  node -e 'const h=require("node:fs").readFileSync("rooms.html","utf8");
  new Function("require","argv",h.split(`<script id="rooms-node" type="text/plain">`)[1].split(`</script>`)[0])(require,process.argv.slice(1))' "$@"
}

rooms test
rooms init
rooms sync all
rooms serve

Set these environment variables through your private service or secret manager before running the relevant commands. Do not put secrets into this file, a browser, or checked-in shell scripts.

DATABASE_URL             Neon writer connection URL (init / sync)
ROOMS_READ_DATABASE_URL  Optional separate Neon reader URL (serve)
ROOMS_PASSWORD           Required for serve; at least 20 characters
ROOMS_PORT               Optional; defaults to 8787
ROOMS_BLUESKY_ACTOR      Bluesky handle or DID
ROOMS_MASTODON_ORIGIN    HTTPS origin of your Mastodon instance
ROOMS_MASTODON_ID        Numeric account ID on that instance
ROOMS_MASTODON_TOKEN     Optional bearer token if the instance requires it
ROOMS_TYPEFULLY_KEY      Typefully v2 API key
ROOMS_TYPEFULLY_SET      Social set ID to verify and read
ROOMS_X_DIR              Directory of normalized monthly X archive files
ROOMS_X_ACCOUNT_ID       Stable X account ID used in those files

rooms init creates the single rooms_now schema. If using a distinct reader role, grant it USAGE on that schema and SELECT on its two tables; do not grant it write access. The service binds to 127.0.0.1 and uses HTTP Basic authentication (user rooms). Put it behind a private HTTPS reverse proxy that forwards Authorization. Do not expose the loopback HTTP service directly. Schedule rooms sync all out of band; dashboard refresh only rereads Neon.

Normalize the existing X archive

The original archive format was not supplied. Map it to one UTF-8 JSON file per reporting month, named YYYY-MM.json. This is a format example, not dashboard data:

{
  "month": "2025-08",
  "accountId": "123",
  "accounts": [
    {"observedAt":"2025-08-31T23:50:00Z","name":"Rooms",
     "metrics":{"followers":128,"following":null}}
  ],
  "posts": [
    {"id":"456","observedAt":"2025-09-01T09:00:00Z",
     "publishedAt":"2025-08-12T16:00:00Z","basis":"month",
     "metrics":{"impressions":820,"likes":null}}
  ]
}

Account metrics are point-in-time totals: followers, following, posts. Post metrics: likes, replies, reposts, quotes, impressions. Use basis: "month" only for counts measured over that reporting month; use basis: "snapshot" for reported cumulative counts. If a post has both, supply two records. Preserve real observation timestamps and string IDs. Omit unknown counts or use null; do not insert zero or invent dates. If the export does not establish a metric’s window, omit the metric until it can be mapped. The archive is never marked complete based on filenames alone.

What qualifies as a live readback?

rooms test checks fixture behavior without credentials. rooms sync all calls the configured sources and ingests the local X archive. For each source it commits one run, opens an independent Neon connection, and checks the stored run metadata and normalized rows against the input, including row count and SHA-256. Only then does it save a receipt and make the run eligible for analytics. A receipt on a failed collection proves that the failure was recorded, not that source access worked.

For acceptance, run rooms sync all with your real credentials and archive. Check all four receipts, confirm neither official feed returned a collection error, and open the authenticated dashboard to confirm the matching receipts. Typefully must find the configured social set and read its drafts endpoint; it may legitimately return zero published records in the page. A command exit of 0 means collection completed at the documented scope and readback matched, not that coverage was exhaustive. Inspect the source notes for missing archive months and compare an archived metric with its original export. Without this run, live acceptance remains unverified.

Measurement rules

Bluesky uses the official public AppView for account totals and the first author-feed page. Mastodon uses the configured instance’s official account and status APIs; reported counts may differ from other instances. Only public, original posts are included; Bluesky replies are excluded, while public Mastodon replies may appear. Typefully contributes published metadata only from the first drafts page; this integration does not read any engagement counters from Typefully. Nothing is joined across networks or matched by post text.

Account trends show up to 48 real observations per account, with no interpolation. Post rankings use the latest observation per post and window, from at most 120 recently observed posts per source/window and the 24 latest available X monthly windows. The table shows up to 30 of those candidates. Snapshot ranks are raw totals with different observation dates and post ages, not comparable rates. A source can be recent while some retained posts are old. Live source freshness is flagged after 48 hours; X is flagged when the last populated archive month predates the last closed UTC month.
