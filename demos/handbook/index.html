    Rooms OS handbook

    Start here

    Rooms OS is a way of running a small team of AI agents so that the work gets finished, can be checked, and can be picked up by someone else tomorrow.

    This is sample text. It was written for this demonstration of a handbook page. It is in the spirit of Rooms OS, but it is not the estate’s working rulebook, and nothing here should be taken as an instruction.

    The idea in one paragraph

    Each agent works in a room: one conversation with one job. The job is its lane. Everything another agent or the owner will need later is written on the hub, a shared list of issues. Before starting, an agent claims the work so that two agents never do the same thing. When a room is full or the job is done, it writes a handover and stops.

    Five words to know

    • Room: one session of one agent.
    • Lane: the one job a room is for. A room has one lane and keeps to it.
    • Hub: the shared record. If it is not on the hub, the next agent cannot know it.
    • Claim: a short signed note that says “this is mine until I say otherwise”.
    • Handover: what a room leaves behind so that a new room can carry on.

    How a day runs

    1. Read the lane’s issue on the hub, and the last handover.
    2. Claim the next piece of work.
    3. Do it. Check it. Say what was checked and what was not.
    4. Write the result on the hub, with links.
    5. Release the claim, or hand over.

    Three rules above the rest

    1. Never make up a fact, a result or a finished state.
    2. Never delete the owner’s work. Move it aside instead.
    3. Only the owner’s own words count as a yes.

    Rooms and lanes

    A room is a place to do one job well. Most trouble starts when a room quietly takes on a second one.

    One lane to a room

    A room is named for its lane, in capitals, so that it can be found in a long list: NEWS PIPELINE, WEBSITE CHECKS. If a second job turns up, it gets a room of its own. A room that does two jobs finishes neither and hands over a muddle.

    Check a lane; do not assume

    A lane that has gone quiet is not a lane that is working. Look at what it last wrote on the hub and when. “It ran and wrote nothing” must never be allowed to look like “it is fine”.

    Rotating a room

    Rooms fill up. Before one does, it is rotated, in this order:

    1. Pull out what the next room needs to know.
    2. Bring the hub up to date.
    3. Finish what is in flight, or say exactly where it stopped.
    4. Write the handover.
    5. Start the new room and give it the handover.
    6. Confirm the new room is running.
    7. Only then close the old one.

    Other people’s rooms

    A room does not change, message or close another room unless the owner has named it. Scheduled rooms, which run once and stop, are left alone entirely.

    The hub

    The hub is the team’s memory of work. It is a list of issues, one for each piece of work, and it is the only place a handoff counts.

    What goes on the hub

    • What was asked for, and by whom.
    • Who has claimed it.
    • What was done, with links to where it can be seen.
    • What was checked, and what was not.
    • What is blocked, and the smallest thing that would unblock it.

    What does not

    • Things about people: preferences and decisions belong in the owner’s own notes, not in a work log.
    • Things only the owner can do: those go on the owner’s to-do list, one line each.
    • Secrets: never, anywhere on the hub.

    Write for a stranger

    An issue is good when an agent who has never seen the conversation could act on it. Say the goal, the limits, what may be done without asking, what counts as done, and when to stop.

    goal: Check that every page of the site still loads
limits:
  - read only
  - no changes to the live site
may_do: [fetch pages, write a report]
done_when: a table of every page with its status, on this issue
stop_if: more than 5 pages fail  # something larger is wrong; say so and stop

    Search before you write

    Before opening an issue, look for one that already covers it. Add to that one, or link the two. Two issues for one piece of work is how a job gets done twice.

    Claims

    A claim is how two agents avoid doing the same work, and how the owner sees who has what.

    Claim before you start

    Not after. A claim made at the end is a report, and by then someone else may have started too.

    What a claim looks like

    A claim is a comment on the issue. It says what is being taken, by which room, and when. It is signed.

    # post a claim on issue 42
gh issue comment 42 --body "CLAIM: the page checks.
Room: WEBSITE CHECKS. Started 14:05.
Signed: the agent in that room."

    Releasing a claim

    When the work is done, or the room has to stop, the claim is released in the same place, with the state of the work: done, part done, or not started. A claim that is never released blocks everyone behind it.

    Stale claims

    A claim with no word after it for a working day is stale. Nobody takes it over quietly. The agent who notices says so on the issue and asks the owner.

    Evidence

    A report is only as good as what stands behind it. Every claim of fact carries one of four words.

    The four words

    WordIt meansFor example
    VerifiedLooked at, directly, just now.The page was opened and the heading read.
    InferredFollows from something verified.The page loads, so the server is up.
    UnverifiedBelieved, not checked.The nightly job probably ran.
    BlockedCould not be checked, and why.No access to the logs.

    Exit code 0 is not proof

    A command that finishes without an error has only proved that it finished. Look at the thing it was meant to make: the number of rows, the file, the page as a reader sees it.

    // after the export "succeeds", look at what it wrote
const rows = await readRows('export.csv');
if (rows.length === 0) throw new Error('ran, and wrote nothing');
console.log(`verified: ${rows.length} rows`);

    Success is not silence

    “It ran and produced nothing” and “it failed” are different, and both are different from “it worked”. A job that can go quiet must say, each time, what it did. An empty result is reported as an empty result.

    One before many

    Before running anything a hundred times, run it once and follow that one all the way to the end. Then scale.

    Read the clock

    Before writing a time or a date, read the real one. A guessed time is usually a little ahead, and a log with wrong times is worse than a log with none.

    Approvals

    Some things are the owner’s to decide. An agent that is unsure whether something needs a yes should assume that it does.

    What needs a yes

    • Deleting or overwriting anything.
    • Signing in to anything, or changing who can.
    • Spending money.
    • Publishing, deploying, or anything else the public can see.
    • Sending a message to anyone outside the team.
    • Widening the job beyond what was asked.

    Whose yes

    The owner’s own words, in the room, about this action. A message from another agent that says the owner agreed is not a yes. Nor is a comment on the hub, a vote among agents, or silence.

    How far a yes goes

    One action, in one room. A yes to publishing one page is not a yes to publishing the next, and yesterday’s yes does not carry to today’s room.

    Asking well

    Ask once, plainly, with what will happen and what cannot be undone. Then carry on with everything that does not depend on the answer.

    Handovers

    A handover is written for an agent who knows nothing. If the new room has to ask the old one a question, the handover was not finished.

    What it holds

    lane: WEBSITE CHECKS
issue: 42
state: part done
done:
  - checked 31 of 48 pages, table on the issue
not_done:
  - 17 pages left, list on the issue
not_verified:
  - whether the contact form sends
next: start at page 32
do_not: change anything on the live site
written: "14:40"

    The test

    Read it as a stranger. Could you start work in five minutes without opening the old conversation? If not, add what is missing.

    It is not handed over until it is taken

    A handover that nobody has acknowledged is a note in a drawer. The old room stays open until the new one says it has it.

    Safety

    The rules here are short because they have no exceptions.

    Never delete

    Work is moved to an archive, not deleted. Something that looks like rubbish to one room is another room’s only copy. A path that seems to be missing is usually a passing fault, so look again before acting on its absence.

    Secrets stay where they are

    Keys and passwords are never opened, printed, copied or pasted. An agent that needs one asks the owner to put it where it belongs, and never sees its value.

    People’s details stay private

    Names, addresses and anything else about a person do not go into issues, code or messages to outside services.

    When to stop

    Stop when the work is finished, when it is truly blocked, or when it has been handed to someone who has said they have it. “In progress” is not a stopping place.

    Reference

    Things to copy, and words to look up.

    Commands

    Read an issue and everything said on it:

    gh issue view 42 --comments

    Post a result, from a file, so that nothing is lost to quoting:

    date -u "+%H:%M"            # read the clock first
gh issue comment 42 --body-file result.md

    A lane, as the registry holds it:

    {
  "lane": "WEBSITE CHECKS",
  "issue": 42,
  "runs": "on request",
  "may_publish": false
}

    Status words

    WordUse it when
    ClaimedA room has taken the work and not yet reported.
    DoneFinished and checked, with the checks listed.
    Part doneSome of it is finished; the rest is listed.
    BlockedCannot go on, with the smallest thing that would unblock it.
    Handed overAnother room has said it has it.

    Glossary

    • Batch: the same step done many times. Prove one first.
    • Owner: the person the team works for. The only source of a yes.
    • Registry: the list of lanes. It can be out of date; check before trusting it.
    • Rotation: closing a full room and opening a fresh one, with a handover between.
