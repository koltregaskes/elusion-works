# Website monetisation design study
Research checked **12 November 2026**. Mock-ups only. No payment integration, accounts, wallets, credentials or live advertisements.

## December decision
Use one hosted support route, one shared support page and a quiet footer across the network. **Prefer Stripe Payment Links for tips for the published work**, conditional on Stripe accepting the business/use case and the account owner approving public receipt details. No Worker is needed for a hosted link. If creator-facing presentation matters more, choose **Ko-fi Free linked to Stripe instead**, with Standard switched off. Do not launch both competing primary routes.

Do not describe this commercial creative network as a charity. Stripe distinguishes tips for supplied work from donations for a specific charitable purpose and excludes personal money transfers. Confirm the description with Stripe before activation. [Stripe use restrictions](https://support.stripe.com/questions/requirements-for-accepting-tips-or-donations?locale=en-GB)

Defer crypto, ad networks, memberships, fiscal hosting and bespoke Checkout until demand justifies their upkeep. A direct sponsor could be considered later, after approval of the exact sponsor, copy, destination and desktop/mobile placement. Nothing in this study authorises activation.

## Static-site architecture, design only
Payment Links: static support button → Stripe-hosted payment page → confirmation. No site-side SDK, API endpoint or Worker is necessary. Customer-chosen amounts are supported. [Payment Links donations and amounts](https://support.stripe.com/questions/how-to-accept-donations-through-stripe?locale=en-US)

If custom Checkout is later justified: static page → restricted Worker endpoint → Stripe Checkout Session → hosted Checkout. The future design would validate amount/currency on the server, restrict origins, rate-limit requests, keep credentials in managed secrets, verify signed webhooks and deduplicate events. A return-page visit is not proof of payment. No endpoint, SDK, webhook or secret binding is included here.

## UK tax and records
Tips linked to content, sponsor income, affiliate commissions and sales can be business/trading income. Calling a payment a donation does not settle its tax treatment. HMRC's £1,000 trading allowance applies across relevant gross income sources per tax year, not per platform or website. Company receipts and personal trading have different rules; determine the receiving entity privately. [HMRC online-platform income](https://www.gov.uk/guidance/check-if-you-need-to-tell-hmrc-about-your-income-from-online-platforms)

Freely given support with nothing supplied in return can fall outside VAT; sponsorship with promotional benefits or paid products/services requires a separate VAT analysis. No Gift Aid or charitable deduction should be promised for this network. [HMRC sponsorship/VAT](https://www.gov.uk/guidance/sponsorship-and-vat-notice-70141)

Crypto received as income needs a GBP value and fee record at receipt. A later sale, swap or spend may create a separate Capital Gains Tax event. Genuine gifts can have different treatment, so resolve classification first. [HMRC receipt](https://www.gov.uk/guidance/check-if-you-need-to-pay-tax-when-you-receive-cryptoassets), [HMRC disposal](https://www.gov.uk/guidance/check-if-you-need-to-pay-tax-when-you-sell-cryptoassets). Keep dated gross/fee/net/refund and transaction records privately, never in this repository.

## Other modest monetisation ideas
Offer one evergreen download, template or licensed creative asset after demand appears; a clear licence and reliable delivery are necessary. A small fixed-scope service can earn from a tiny audience but costs time, so cap availability. Carefully disclosed affiliate links for tools already recommended may fit resource pages, but assess programme eligibility, tracking consent, minimum payouts and editorial conflicts individually. Do not create a recurring reward schedule before a sustainable publishing routine exists. None of these has a revenue forecast or an account opened here.

## Viewing and integration boundary
Open any HTML file directly in a browser, or the T3 files viewer. Each is self-contained with inline CSS, system fonts, responsive layouts, disabled buttons and no scripts, external resources, forms or payment destinations.

- [Donation block](donation-block.html): after a useful article/tool; card, amount choice, alternate provider and explicitly empty crypto QR space.
- [Support footer](support-footer.html): reused across site types, leading to the shared support page.
- [Sponsor slot](sponsor-slot.html): fictional direct sponsor, visibly labelled Advertisement.
- [Support the network](support-network.html): umbrella support page using the existing copper/dark visual direction.

The existing Pages workflow uses an explicit copy list which excludes design/. No live page, navigation, deployment file or payment code changes are proposed. The repository ignores design/ for local git staging; these requested design files are deliberately committed through the GitHub API. Do not broaden deployment or remove that ignore rule as part of review.

Before future activation: owner selects provider and receiving entity, completes onboarding privately, approves receipt/privacy text and exact UI, and separately authorises implementation. Crypto and ads each retain their separate decision. Review does not equal approval to publish.
